# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

kopsrox — a Python CLI that creates and manages HA k3s clusters on Proxmox VE using pve-microvm microvms (https://github.com/rcarmo/pve-microvm). It builds an OCI-image-based microvm template via a patched copy of `pve-microvm-template` with k3s already baked in, clones it into master/worker nodes, and configures + starts k3s on each node via the Proxmox qemu-guest-agent (no SSH, no cloud-init), and wires in kube-vip and the k3s local-path provisioner. This checkout ("anchovy") is a working copy: `kopsrox.ini` here points at a live Proxmox host with real credentials, and most commands mutate that live environment.

No Proxmox cloud-controller-manager or CSI driver on microvm: the guest has no DMI so the CCM's SMBIOS-UUID check can never pass (kubelet's `--provider-id` flag covers providerID instead), and the CSI driver needs disk hotplug, which pve-microvm doesn't deliver into running guests (QEMU-level hot-add works behind cold-plugged pcie-root-ports, but pve-microvm's hotplug path only writes config — re-adding CSI would need a pve-microvm patch plus pciehp/udev in the guest).

## Running it

```
./kopsrox.py [verb] [command] [arg]
```

Verbs and their commands are declared in the `cmds` dict at the top of `kopsrox.py` — that dict is the single source of truth for the CLI surface. Running with no args prints help; running with no `kopsrox.ini` present generates a default one (from `lib/kopsrox_ini.py`) and exits.

- Python deps: `proxmoxer`, `requests`, `urllib3` (no requirements.txt — install manually).
- Host deps: pve-microvm ≥ 0.3.19 on the Proxmox node (`image` commands enforce this and print a notice when upstream has a newer release), the kopsrox microvm kernel (one-time build via `dev/build-kopsrox-kernel.sh` — the stock pve-microvm kernel lacks VXLAN/veth/netfilter/BPF bits k3s needs), and `qm`/`pve-microvm-template` via sudo during `image create`.
- There is no build step, linter, or unit test suite. `dev/testing.sh` is a manual integration test that creates/destroys real clusters against the configured Proxmox host — treat it as destructive.
- Releases: push a `v*` tag — `.github/workflows/release.yml` syntax-checks, packages a tarball, and creates the GitHub release with generated notes.
- `dev/kubectl.sh` wraps kubectl with the exported `<cluster_name>.kubeconfig`; other `dev/*.sh` scripts are similar one-liner conveniences.
- `dev/gen_config.sh` regenerates the default ini as `kopsrox.ini.default` without clobbering the real config.

## Architecture

Execution is explicit dispatch, not import side effects:

1. `kopsrox.py` validates argv against the `cmds` dict (verb, then command, then any required arg), then calls `kopsrox_config.init(verb, cmd)` followed by `__import__('verb_' + verb).run(cmd, arg)`. `arg` is `' '.join(sys.argv[3:])` (not just `argv[3]`), so unquoted multi-word arguments keep working (`k3s kubectl get pods -A`, `node cluster-exec <command>`). Each `lib/verb_*.py` defines `run(cmd: str, arg: str | None) -> None`, which dispatches on `cmd`; nothing runs at import time.
2. Every module uses explicit `from x import name1, name2, ...` — no `import *` anywhere. `verb_*` modules import what they need from `kopsrox_k3s`, `kopsrox_proxmox`, `kopsrox_artifacts`, `kopsrox_config` and `kopsrox_kmsg` directly, rather than relying on a fixed chain.
3. `kopsrox_config.init(verb, cmd)` runs the staged checks (called explicitly from `kopsrox.py` before dispatch, instead of at import time): validates `kopsrox.ini` against the SCHEMA in `lib/kopsrox_schema.py` (injecting every option as a module global via `globals().update(...)`), opens the Proxmox API connection (`prox`), then makes ONE `cluster.resources` call that covers the node/storage/VM/image checks. Side effects are verb-scoped: guest verbs (`cluster`/`k3s`/`etcd`/`node`) power on stopped VMs; `image`+`cluster` ping the master agent (`conf_check_master_up`); image-only checks (pve-microvm version, bridge/SDN) run under `image`. For every verb (once the image is confirmed to exist), it also fetches the image's description (`cloud_image_desc`) and compares the `k3s_version:` baked into it against the configured `k3s_version` in the ini, printing a non-fatal notice to run `image update` (then `k3s upgrade`) on a mismatch — same pattern as the pve-microvm-latest-release notice below it. Adding a config option means adding ONE `opt(...)` entry to `SCHEMA` in `lib/kopsrox_schema.py` — it drives validation, the global name (`var=` for ini names with hyphens), and the generated default ini (comments included; `lib/kopsrox_ini.py` just renders it). `kopsrox_schema.py` is pure and must never import `kopsrox_config` (the default ini is generated exactly when `kopsrox.ini` is missing); `kopsrox_config.py` is a plain importable module — `init(verb, cmd)` takes both as arguments instead of reading `sys.argv` itself, so it can be imported outside the CLI entrypoint. `dev/test_config.py` tests the schema/renderer (via `kopsrox_schema`) without touching Proxmox.

Key modules:

- `lib/kopsrox_proxmox.py` — Proxmox primitives: `qa_exec()` (run a command inside a VM via qemu-guest-agent, polling until exit — this is how ALL in-VM work happens; the agent runs over virtio-serial, so it works before networking is up — each call has a fixed ~0.5-1s protocol round-trip cost regardless of what it runs, so batch multiple operations into one script rather than many small calls), `qa_write()` (push a file into a VM via the agent file-write API, chunked above 40KiB — always followed by its own `chmod` call), `node_prepare()` (post-clone, per-node identity only: disables pve-microvm first-boot services, writes static-IP networkd config + iproute2 fallback unit + hostname, wipes machine-id, grows the root fs, then reboots and verifies IP/internet; idempotent via `/etc/kopsrox-node-init-done` — everything cluster-wide instead of per-node — k3s, the local user, DNS, `extra_packages`, the kube-vip/traefik manifest — is baked into the image once at build time, see `verb_image.py`. Everything before the reboot is bundled into one heredoc-based script pushed and run via a single `qa_write`+`qa_exec` — this used to be ~15 separate round trips; batching cut the pre-reboot portion from ~13s to ~4.4s per node), `node_reboot_wait()`, `clone()`, `prox_destroy()`, `prox_task()` (blocks until a Proxmox task finishes and checks exit status).
- `lib/kopsrox_k3s.py` — cluster logic: `k3s_join()` (writes this node's role-aware `config.yaml` — no manifest write for a normal join, that's baked into the image too — then `systemctl enable --now` the systemd unit already baked into the image; no install, no internet dependency at join time; `token` defaults to the saved token file so recreating a cluster of the same name is deterministic, but pass `token=''` to force a fresh identity), `k3s_service()` (maps nodetype to the baked-in unit: `k3s` for master/slave/restore, `k3s-agent` for worker), `k3s_init_node()` (master/slave/worker/restore, calls `k3s_join()` then waits for Ready; `restore` bootstraps a fresh single-node master with `k3s_join(vmid, 'master', token='')` — pinning the old saved token here conflicts with the new CA `--cluster-init` generates and crashes k3s outright — optionally looks up the latest S3 snapshot via `k3s etcd-snapshot ls`, then `--cluster-reset --cluster-reset-restore-path=...`, then re-writes the kube-vip/traefik manifest since the reset's `rm -rf /var/lib/rancher` wipes it and nothing else will), `k3s_update_cluster()` (reconciles running VMs against `masters`/`workers` in the ini, adding or draining+removing nodes), `k3s_upgrade_cluster()` (`k3s upgrade` — re-runs the k3s installer live against every running node with `INSTALL_K3S_VERSION` set to the configured `k3s_version`, no `SKIP_START`/`SKIP_ENABLE` this time so the installer restarts the service itself once it detects the binary changed; masters one at a time first to keep etcd quorum, then workers; `verb_k3s.py` also runs `image update` straight after so the image doesn't drift from the live cluster again), kubeconfig/token export, `kubectl()` (runs kubectl on the master via qa_exec). `export_k3s_token(restore=False)` compares the live token against the saved one and aborts on a password mismatch — except when `restore=True`, since `k3s server --cluster-reset` always mints an entirely new token (not just a new CA), so a changed password after a genuine restore is expected. With no cloud controller, kopsrox owns node-object lifecycle itself: `k3s_remove_node()` deletes both the node object AND its `<node>.node-password.k3s` secret (k3s rejects a rebuilt node reusing the name otherwise), and `cluster restore` purges stale node objects/secrets from the restored datastore before rebuilding. `k3s_check()` matches `\bReady\b` deliberately — plain `Ready` also matches `NotReady` and once made restores skip re-adding k3s config on rebuilt nodes entirely.
- `lib/kopsrox_artifacts.py` — generator functions for all cluster artifacts: kubevip/traefik manifest, and `k3s_config(nodetype, vmid, token)` — a role-aware `/etc/rancher/k3s/config.yaml` (master gets `cluster-init: true` + etcd-s3 settings; slave gets the same plus `server:`/`token:` to join; worker gets a minimal agent config with just `server:`/`token:`/`kubelet-arg:`), since every k3s flag a node needs is supplied this way rather than on the command line. Called by `verb_image.py` (writes an inspection copy under `lib/manifests/` — gitignored/generated, never edit directly) and by `kopsrox_k3s.k3s_join()` (writes the real, node-specific copy at join time via the guest agent).
- `lib/verb_image.py` — `image create` builds the microvm template and bakes in everything that is identical across every node in the cluster: writes a patched copy of `pve-microvm-template` to `lib/scripts/microvm-template.sh` (upstream's chroot install fails silently on ubuntu's empty `/etc/resolv.conf`, and its first-boot installer would block the guest agent behind a network that doesn't exist yet — each patch is asserted so upstream changes fail loudly), runs it, verifies the rootfs actually has systemd + qemu-ga by ro-mounting the template disk, `sudo qm set --args` to boot the kopsrox kernel (`args` is root-only, so shell not API), then boots the template once via the guest agent to: run the k3s installer twice with `INSTALL_K3S_SKIP_START`/`INSTALL_K3S_SKIP_ENABLE` — once as `server` (produces `k3s.service`, shared by master/slave), once as `agent` (produces the separate `k3s-agent.service` for workers) — create the `localuser` account (password, SSH key, sudoers), write `/etc/resolv.conf`, install `extra_packages`, and write the kube-vip/traefik manifest — before a graceful agent-driven shutdown and tagging. Only genuinely per-node state (static IP, hostname, machine-id, root fs resize) is left to `node_prepare()`/`kopsrox_k3s.k3s_join()` at clone/join time. Bumping `k3s_version`, `localuser`/`localpass`/`localsshkey`, `network_dns`, or `extra_packages` in the ini now requires `image update` before it takes effect (previously they took effect on the next node join).
- `lib/kopsrox_kmsg.py` — the only module that emits ANSI; all user output goes through it. `kmsg(kname, msg, sev)` prints a glyph + severity-colored line (`kname` is `scope_action`, split on the first `_`; `sev` is `info`/`sys`/`err`); `kabort(kname, msg)` is `err` + `exit(1)`; `kstep(kname, msg)` is a context manager showing a live spinner with elapsed time (`quiet=True` for polling internals like `qa_exec`/`prox_task` — nothing printed on success); `kplan(add, title)`/`kplan_tick()` drive the overall `4/9` progress bar in compound verbs (`cluster create/update/restore/destroy`, `image create`). Output degrades to plain sequential lines when stdout is not a tty; `NO_COLOR` disables color. `dev/test_kmsg.py` tests the module standalone (scripted asserts when piped, visual demo on a tty).

VM ID / naming convention (defined by `suffixes`/`vmnames` in `kopsrox_config.py`): `cluster_id` = template `-i0`, `+1..+3` = masters `-m1..-m3` (m1's ID is `masterid`), `+4` = utility `-u1`, `+5..+9` = workers `-w1..-w5`. Each VM's IP is derived arithmetically: `network_ip`'s last octet + (vmid − cluster_id). `network_ip` itself is the kube-vip VIP. Only 1 or 3 masters are supported.

Microvm specifics and traps (each of these was learned the hard way):

- `machine: microvm` with direct kernel boot — no BIOS/UEFI, no cloud-init drive, no `boot=order`. Static IP/MTU is applied in-guest by `node_prepare()` via the agent (`ipconfig0`/`net0 mtu=` are no-ops for microvms); DNS and the local user are baked into the image instead (see `verb_image.py`).
- The guest kernel is custom-built (`dev/build-kopsrox-kernel.sh` + `lib/scripts/kopsrox-kernel.config`) because guests have no `/lib/modules` — every feature k3s needs must be `=y`. When adding kernel options, audit the final `.config`: `olddefconfig` silently drops options with unmet dependencies (most `xt_*` need `NETFILTER_ADVANCED=y`).
- The kopsrox kernel's built-in DUMMY/SIT create `dummy0`/`sit0` in guests, so network matching must use `Driver=virtio_net`, never `Type=ether` (which once assigned the node IP to dummy0 and blackholed the default route).
- Guests boot in ~1s. The 90s-boot failure mode is udev missing from the image (device units never appear, `serial-getty` waits on `dev-ttyS0.device` forever) — the template installs udev/sudo/systemd-timesyncd on top of upstream's package set, plus `net.ifnames=0` on the kernel cmdline so udev doesn't rename `eth0` (kube-vip's manifest hardcodes it).
- `qm stop` is a hard power-cut (no ACPI): guest page-cache writes are lost, so never stop a node to "check" something that was just written inside it. Debug live — the serial console accepts input only with `\r` line endings (via socat on `/var/run/qemu-server/<vmid>.serial0`).
- `qm shutdown`/`qm reboot` need pve-microvm ≥ 0.3.19 (our upstream fix: qmeventd socket + dbus; #13/#14). kopsrox's own reboots use `node_reboot_wait()` (in-guest `systemctl reboot`, detected by boot-id change — microvms reboot too fast for agent-down polling). A VM stuck in `paused (shutdown)` recovers with `qm stop` + `qm start`.
- `node_reboot_wait()`'s own timing is inherently variable (measured 7.9s/35.3s/27.9s on three consecutive reboots of the same already-stable node, nothing else running) — this is virtio-serial/qemu-guest-agent reconnection variance after a guest kernel reboot, not the guest itself being slow (`systemd-analyze` on the same node confirms the guest boots in ~1.1s every time). Don't read a slow `node_prepare()`/`proxmox:reboot` step as a regression in whatever ran just before it without checking `systemd-analyze` first.
- pvedaemon holds pve-microvm's perl code in memory: on pve-microvm < 0.3.20, `systemctl restart pvedaemon` after install/upgrade or API-started VMs (everything kopsrox starts) silently run the old code (0.3.20+ postinst restarts it itself).
- Every node's image has BOTH `k3s.service` and `k3s-agent.service` baked in (so any clone can become master/slave or worker) — this means k3s's own `k3s-uninstall.sh`/`k3s-agent-uninstall.sh` must never be used to remove k3s from a node: its "another k3s service installed" guard always trips (both units always exist) so it skips cleaning up the shared binary/data, and it unconditionally deletes its own unit file first regardless, which nothing can regenerate short of an `image update`. `node_k3s_uninstall()` uses the generic, role-agnostic `k3s-killall.sh` instead and wipes `/var/lib/rancher`/`/etc/rancher/k3s` by hand, leaving the baked-in units untouched for the next `k3s_join()` to reuse.

Error-handling convention: errors go through `kabort(kname, msg)` — an `err` line then `exit(1)`; success paths exit 0. Broad `except Exception:` around attribute/index access is still common (no bare `except:` remains in `lib/`/`kopsrox.py`, so `SystemExit`/`KeyboardInterrupt` always propagate); SystemExit-as-control-flow (an `exit()` inside `try` caught by a broad `except`) has been removed — don't reintroduce it.

## Cluster artifacts in repo root

`<cluster_name>.kubeconfig` and `<cluster_name>.k3stoken` are exported per cluster and are required for restore operations (`etcd restore` compares the saved token's password against the live one). Etcd snapshots go to the S3 endpoint configured in the ini; `cluster restore` rebuilds the whole cluster from the latest snapshot, purging stale node objects/password secrets before rebuilding workers.
