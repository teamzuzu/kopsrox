# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

kopsrox — a Python CLI that creates and manages HA k3s clusters on Proxmox VE using pve-microvm microvms (https://github.com/rcarmo/pve-microvm). It builds an OCI-image-based microvm template via a patched copy of `pve-microvm-template` with k3s already baked in, clones it into master/worker nodes, and configures + starts k3s on each node via the Proxmox qemu-guest-agent (no SSH, no cloud-init), and wires in kube-vip and the k3s local-path provisioner. kopsrox runs **on the Proxmox node itself** and drives it through the local `qm`/`pvesm`/`pvesh` CLIs (via `sudo`) — there is no HTTP API connection, so no endpoint/user/token config. This checkout ("anchovy") is a working copy running on the live node `leopard`, and most commands mutate that live environment.

No Proxmox cloud-controller-manager or CSI driver on microvm: the guest has no DMI so the CCM's SMBIOS-UUID check can never pass, and the CSI driver needs disk hotplug, which pve-microvm doesn't deliver into running guests (QEMU-level hot-add works behind cold-plugged pcie-root-ports, but pve-microvm's hotplug path only writes config — re-adding CSI would need a pve-microvm patch plus pciehp/udev in the guest).

## Running it

```
./kopsrox.py [verb] [command] [arg]
```

Verbs and their commands are declared in the `cmds` dict at the top of `kopsrox.py` — that dict is the single source of truth for the CLI surface. Running with no args prints help; running with no `kopsrox.ini` present generates a default one (`init_kopsrox_ini()` in `lib/kopsrox_schema.py`) and exits.

- Python deps: `requests` only (no requirements.txt — install manually). Everything else is stdlib; kopsrox talks to Proxmox through the local `qm`/`pvesm`/`pvesh` CLIs, not an HTTP client.
- Host deps: pve-microvm ≥ 0.3.24 on the Proxmox node (`image` commands enforce this and print a notice when upstream has a newer release), the kopsrox microvm kernel (one-time build via `dev/build-kopsrox-kernel.sh` — the stock pve-microvm kernel lacks VXLAN/veth/netfilter/BPF bits k3s needs), and `qm`/`pve-microvm-template` via sudo during `image create`.
- There is no build step, linter, or unit test suite. `dev/testing.sh` is a manual integration test that creates/destroys real clusters against the configured Proxmox host — treat it as destructive.
- Releases: push a `v*` tag — `.github/workflows/release.yml` syntax-checks, packages a tarball, and creates the GitHub release with generated notes.
- `dev/kubectl.sh` wraps kubectl with the exported `<cluster_name>.kubeconfig`; other `dev/*.sh` scripts are similar one-liner conveniences.
- `dev/gen_config.sh` regenerates the default ini as `kopsrox.ini.default` without clobbering the real config.

## Architecture

Execution is explicit dispatch, not import side effects:

1. `kopsrox.py` validates argv against the `cmds` dict (verb, then command, then any required arg), then calls `kopsrox_config.init(verb, cmd)` followed by `__import__('verb_' + verb).run(cmd, arg)`. `arg` is `' '.join(sys.argv[3:])` (not just `argv[3]`), so unquoted multi-word arguments keep working (`k3s kubectl get pods -A`, `cluster exec <command>`). Each `lib/verb_*.py` defines `run(cmd: str, arg: str | None) -> None`, which dispatches on `cmd`; nothing runs at import time.
2. Every module uses explicit `from x import name1, name2, ...` — no `import *` anywhere. `verb_*` modules import what they need from `kopsrox_k3s`, `kopsrox_proxmox`, `kopsrox_artifacts`, `kopsrox_config` and `kopsrox_kmsg` directly, rather than relying on a fixed chain.
3. `kopsrox_config.init(verb, cmd)` runs the staged checks (called explicitly from `kopsrox.py` before dispatch, instead of at import time): validates `kopsrox.ini` against the SCHEMA in `lib/kopsrox_schema.py` (injecting every option as a module global via `globals().update(...)`), then discovers state WITHOUT any `qm`/`pvesh`/`pvesm` spawn (each of those pays ~1.4s of pve-perl startup, so per-invocation count dominates wall time). The node name is the host's own hostname (`socket.gethostname()`, so there is no `proxmox_node` option); everything else comes from one cheap `sudo bash -c` that reads the pmxcfs/runtime files directly — `/etc/pve/storage.cfg` (storage exists), `/etc/pve/qemu-server/<vmid>.conf` (VMs on this node — that dir symlinks to the local node's), `/var/run/qemu-server/<vmid>.pid` + `kill -0` (running vs stopped, the same signal `qm status` keys on), and the template's own `.conf` tacked on (its `#`-comment lines are the URL-encoded image description, and the `scsi0:` line is the disk volid, cached for `kopsrox_img()`). All CLI calls go through `kopsrox_config.pve_run()` — a `sudo`-prefixed `subprocess` argv wrapper (argv list, not a shell string, so payloads with quotes/newlines need no escaping; `check=True` kaborts on non-zero exit). `sudo_check()` runs once before the first of those, right after the proxmox-node check: root short-circuits with no spawn, anyone else must pass `sudo -n true`. Without it a sudo password prompt would be written to the *captured* stderr and kopsrox would look hung rather than failed — hence `-n` plus `stdin=DEVNULL` and a timeout, so it can never block whatever the sudoers config. It tests `true` rather than `qm` deliberately: the discovery spawn is `sudo bash -c`, which is equivalent to full root anyway, so a narrowly-scoped sudoers entry cannot work regardless. Side effects are verb-scoped: guest verbs (`cluster`/`k3s`/`etcd`/`node`) power on stopped VMs (`qm start`); the master agent ping (`conf_check_master_up`, a real ~1.4s `qm` spawn) runs only where its result is used — the `cluster` verb (plan totals) and `image create` (bridge gate); the image build-prerequisite checks (pve-microvm version, upstream-release notice, guest-kernel drift notice, bridge/SDN *discovery* via `pvesh get`) run only under `image create`, not `image info`/`destroy`. The one bridge step that is NOT gated is the string normalisation of an SDN `network_bridge` (`sdn/<zone>/<vnet>` → `<vnet>`, with the zone kept in `sdn_zone` for the discovery call): it costs no spawn, and it used to sit inside the `image create` gate, so every other verb cloned with `--net0 bridge=sdn/<zone>/<vnet>` verbatim. So a read-only command like `image info` makes zero pve-perl spawns and returns in ~0.3s. For every verb (once the image is confirmed to exist), it also fetches the image's description (`cloud_image_desc`) for the **config-drift** comparison. Three groups drift: the `k3s_version:` baked into the image description, `IMAGE_CONFIG_OPTS` (oci_image, localuser/pass/sshkey, network_dns, extra_packages, nfs_*) and `CLUSTER_CONFIG_OPTS` (s3_*, masters, workers, kubelet_args). The latter two each get a short `config_hash()` recorded at the point they take effect — the image group in the i0 template description at `image create`, the cluster group in the m1 master description at the end of `k3s_update_cluster` (create/update/restore). `config_drift()` re-reads both descriptions (already free — the m1 `.conf` is fetched in the same discovery spawn) and returns one ready-to-print line per drifted group, `[]` when clean; an absent baseline is silent, so images/clusters built before the hashes existed never false-positive. Secrets only ever appear hashed, never in plain text in a description. **A normal run prints only a one-line `config drift detected - run "./kopsrox.py config check"` hint**, suppressed for the `RESOLVING_CMDS` that fix drift (`image create`, `cluster create/update/restore`, `config check` itself); the detail lives in `config check`. This is drift *warning*, not a speed optimisation — the comparison itself is ~free, and `config_drift()` is pure given the globals init already set, so `dev/test_config.py` covers it without Proxmox. A third drift notice covers the **guest kernel**: nothing bumps it automatically — it is hand-built by `dev/build-kopsrox-kernel.sh`, is not a package, and is wholly independent of the Proxmox *host* kernel (guests direct-kernel-boot `microvm_kernel` via `qm set --args`, they never use the host's, so a `proxmox-kernel-*` upgrade is a non-event for them). So init fetches upstream's `kernel/version` and compares it against the version read back out of the built binary by `kernel_version()` — which parses the bzImage boot header directly (`HdrS` magic at `0x202`, a 2-byte LE offset at `0x20e` pointing at the nul-terminated version string relative to `0x200`), since the version exists nowhere else: no dpkg entry, and no `/lib/modules` in the guest. It returns `''` for a missing or non-bzImage file and the notice stays silent, as it does when offline or when either version isn't a plain `x.y.z`. A version compare alone is not enough, though: upstream reconfigures the kernel without touching `kernel/version` ( Landlock at 0.3.27, EROFS at 0.3.28 both landed on 6.12.22 ), which would leave a stale kopsrox kernel silently stale forever. So init also hashes the build inputs — `KERNEL_BUILD_INPUTS` ( `version` + `build-kernel.sh` + `pve-microvm-6.12.config` + `pve-microvm-overlay.config`, ~20 KB in total ) concatenated with `lib/scripts/kopsrox-kernel.config` — and compares that against the fingerprint `dev/build-kopsrox-kernel.sh` wrote to `<microvm_kernel>.id` at build time. The two sides hash the same byte stream in the same order, so the tuple and the `cat` in the build script must stay in step. No `.id` file means no baseline and the notice stays silent, the same convention as the image/cluster config hashes. Being network calls, both this (`kernel_notice()`) and the pve-microvm release notice (`microvm_release_notice()`) are reached only from `config check` — `image create` keeps just its two hard gates, the pve-microvm version floor and bridge discovery, plus the existing "kernel not found — run `dev/build-kopsrox-kernel.sh`" check in `verb_image.py`. S3 is **required**, not optional: `etcd snapshot`/`list`/`prune` and `cluster restore` all need it, and since `k3s_config()` pairs `etcd-s3: true` with `etcd-disable-snapshots: true`, k3s only contacts S3 on demand — a bogus endpoint or key builds a perfectly healthy cluster and only surfaces the day a restore needs snapshots that were never taken. So the four non-optional s3 options carry `must_change`, which `resolve()` enforces by rejecting a value still equal to that option's *own* shipped default ( per-option, not the union — a real bucket legitimately named `kopsrox` must still pass ). `s3_region` stays `commented`/`blank_ok`. `must_change` holds the *reason* rather than a bool, so each option explains itself; `localsshkey` carries it too, since it is the only way into a node over ssh. Its placeholder was already rejected before, but only incidentally — `check_sshkey` happened to find it malformed — so the user got a format error instead of being told to set their key. `must_change` runs before `entry['check']`, so the specific message wins while a genuinely malformed key still gets the format error. Schema validation only proves the values are filled in; `verb_config.s3_check()` proves they work, by running `k3s etcd-snapshot ls` on the master — the one call that exercises endpoint, credentials and bucket together. It passes `timeout = 30` because `qa_exec` defaults to 600s and a blackholed endpoint would otherwise hang `config check` for ten minutes. Adding a config option means adding ONE `opt(...)` entry to `SCHEMA` in `lib/kopsrox_schema.py` — it drives validation, the global name (`var=` for ini names with hyphens), and the generated default ini (comments included; `render_ini()`/`init_kopsrox_ini()` in the same module render and write it). `kopsrox_schema.py` is pure and must never import `kopsrox_config` (the default ini is generated exactly when `kopsrox.ini` is missing); `kopsrox_config.py` is a plain importable module — `init(verb, cmd)` takes both as arguments instead of reading `sys.argv` itself, so it can be imported outside the CLI entrypoint. `dev/test_config.py` tests the schema/renderer (via `kopsrox_schema`) and `kernel_version()` (against synthesized bzImage headers) without touching Proxmox.

Key modules:

- `lib/kopsrox_proxmox.py` — Proxmox primitives, all built on `pve_run()` (the sudo/qm/pvesm/pvesh wrapper in `kopsrox_config`): `qa_exec()` (run a command inside a VM via `qm guest exec` — synchronous, waits up to `--timeout` and returns the guest result as JSON: `out-data`/`err-data`/`exitcode`/`exited`. It runs the exec directly ( a single qm spawn on an already-up agent, the common case ); only if that fails does it wait for `qm agent ping` and retry once, so first boot after a clone still works without paying a ping spawn on every call — this is how ALL in-VM work happens; the agent runs over virtio-serial, so it works before networking is up — each call has a fixed ~0.5-1s protocol round-trip cost regardless of what it runs, so batch multiple operations into one script rather than many small calls), `qa_write()` (push a file by base64-encoding the content and piping it via `qm guest exec --pass-stdin` into `base64 -d > path && chmod` — one round trip that also sets the mode; ≤1 MiB, which every kopsrox artifact is, so no chunking; base64 means arbitrary quotes/newlines need no escaping), `node_prepare()` (post-clone, per-node identity only: disables pve-microvm first-boot services, writes static-IP networkd config + iproute2 fallback unit + hostname, regenerates a unique machine-id, grows the root fs, applies the hostname/machine-id/network LIVE, then verifies IP/internet; idempotent via `/etc/kopsrox-node-init-done` — everything cluster-wide instead of per-node — k3s, the local user, DNS, `extra_packages`, the kube-vip/traefik manifest — is baked into the image once at build time, see `verb_image.py`. It's all bundled into one heredoc-based script pushed and run via a single `qa_write`+`qa_exec` — this used to be ~15 separate round trips; batching cut it to ~4.4s per node. There used to be a full guest **reboot** here to bring the new identity/network into effect; applying them live instead — `hostnamectl set-hostname`, `systemd-machine-id-setup` ( committed now, not blanked for boot-time regen ), `networkctl reconfigure` + the idempotent iproute2 fallback for the address/route — is state-for-state identical to what the reboot produced ( verified live: a later reboot converges to the same machine-id/hostname/IP ) and removes 8-35s of variable virtio-serial reconnect latency per node that occasionally left the agent wedged. The one residual difference is cosmetic: the long-running system `dbus-daemon` keeps its old bus machine-UUID until a restart, but nothing in k3s/kube-vip consumes it ( k3s node identity is the hostname )), `node_reboot_wait()` ( now only the `node reboot` command ), `clone()` and `prox_destroy()` (both just run `qm clone`/`set`/`resize`/`start`/`stop`/`destroy` — `qm` is synchronous, so there is no task-polling layer any more; the old `prox_task()`/`task_log()` UPID pollers were deleted when the HTTP API went).
- `lib/kopsrox_k3s.py` — cluster logic: `k3s_join()` (writes this node's role-aware `config.yaml` — no manifest write for a normal join, that's baked into the image too — then `systemctl enable --now` the systemd unit already baked into the image; no install, no internet dependency at join time; `token` defaults to the saved token file so recreating a cluster of the same name is deterministic, but pass `token=''` to force a fresh identity), `k3s_service()` (maps nodetype to the baked-in unit: `k3s` for master/slave/restore, `k3s-agent` for worker), `k3s_init_node()` (master/slave/worker/restore, calls `k3s_join()` then waits for Ready; `restore` bootstraps a throwaway single-node master with `k3s_join(vmid, 'master', token='')` — needed because `k3s etcd-snapshot ls` (used next to validate the named `snapshot`, or pick the latest when it is `None`) requires a running api server to fetch its CA certs; the `token=''` is just a throwaway identity (the `rm -rf` below wipes it before the real restore, so it's irrelevant — `cluster-init` with the saved `K10…` token also works, it simply uses the password part and mints a fresh CA) — then `systemctl stop k3s`, `rm -rf /var/lib/rancher`, and `k3s server --cluster-reset --cluster-reset-restore-path=<snapshot> --token=<saved token>` (the `snapshot` is normalised to a bare basename first — an absolute path would make k3s double the snapshot dir). The `--token` is MANDATORY and MUST be the token the snapshot was taken with: k3s encrypts a snapshot's bootstrap data with the token's password and can only decrypt it with that same token — that's why `<cluster>.k3stoken` is required to restore (checked before `k3s_rm_cluster` in `cluster_restore`, so a missing token doesn't destroy the cluster first). The reset's output is redirected to `/k3s_restore.log`, so it reads the exit code back and `kabort`s on any failure rather than letting an empty `cluster-init` cluster silently boot in the restore's place — the original bug: `--cluster-reset` ran with NO token, fatalled "token does not exist", and that unchecked failure booted a new empty cluster every time, so restore never actually restored (and worse, the follow-on token export overwrote the saved token with the empty cluster's, destroying the only copy needed to ever restore those snapshots). Snapshots are taken UNCOMPRESSED (`etcd-snapshot-compress: false` in `kopsrox_artifacts.k3s_config`) because k3s ≤ 1.34 doubles the path decompressing a compressed one during `--cluster-reset` (`open .../snapshots/var/lib/.../snapshots/x.zip` → fatal → empty cluster) — it is neither S3- nor kopsrox-path specific, an uncompressed snapshot skips the decompress step and restores cleanly. A legacy compressed `.zip` snapshot is still restorable: the first S3 reset downloads it (then fatals on the decompress bug), so the restore path detects the on-disk `.zip`, `unzip`s it, and retries `--cluster-reset --etcd-s3=false --cluster-reset-restore-path=<plain local file>` (the documented local-restore mode). After a good reset it re-writes the kube-vip/traefik manifest since `rm -rf /var/lib/rancher` wipes it and nothing else will, then `systemctl start k3s`), `k3s_update_cluster()` (reconciles running VMs against `masters`/`workers` in the ini, adding or draining+removing nodes), `k3s_upgrade_cluster()` (`k3s upgrade` — re-runs the k3s installer live against every running node with `INSTALL_K3S_VERSION` set to the configured `k3s_version`, no `SKIP_START`/`SKIP_ENABLE` this time so the installer restarts the service itself once it detects the binary changed; masters one at a time first to keep etcd quorum, then workers; `verb_k3s.py` also runs `image create` straight after so the image doesn't drift from the live cluster again), kubeconfig/token export, `kubectl()` (runs kubectl on the master via qa_exec). `export_k3s_token(restore=False)` compares the live token against the saved one and aborts on a password mismatch — except when `restore=True`, since a restore reuses the saved token (it is passed to `--cluster-reset`), so the password is unchanged and only the `K10<ca-hash>` prefix can differ if the snapshot's restored CA differs from the one the saved token was last exported under. NB `--cluster-reset` does NOT mint a new token — it requires the snapshot's original token — so a failed/never-actually-restored run must never overwrite the saved token (the restore path now `kabort`s before export on any reset failure; a silent failure here once destroyed the only copy of the original token). With no cloud controller, kopsrox owns node-object lifecycle itself: `k3s_remove_node()` deletes both the node object AND its `<node>.node-password.k3s` secret (k3s rejects a rebuilt node reusing the name otherwise), and `cluster restore` purges stale node objects/secrets from the restored datastore before rebuilding. `k3s_check()` matches `\bReady\b` deliberately — plain `Ready` also matches `NotReady` and once made restores skip re-adding k3s config on rebuilt nodes entirely.
- `lib/kopsrox_artifacts.py` — generator functions for all cluster artifacts: kubevip/traefik manifest, and `k3s_config(nodetype, token)` — a role-aware `/etc/rancher/k3s/config.yaml` (master gets `cluster-init: true` + etcd-s3 settings; slave gets the same plus `server:`/`token:` to join; worker gets a minimal agent config with just `server:`/`token:`), since every k3s flag a node needs is supplied this way rather than on the command line. An optional `kubelet-arg:` list is appended from the `kubelet_args` ini option (comma-separated, blank → omitted; applies to every role, takes effect on the next join with no image rebuild). There is deliberately no `provider-id` and no `disable-cloud-controller`: both only mattered to the dropped Proxmox CCM/CSI, so k3s runs its embedded cloud-controller-manager and defaults providerID to `k3s://<nodename>`; `servicelb` stays disabled because kube-vip serves LoadBalancer Services (`svc_enable`). The master's config also sets `embedded-registry: true`, which starts k3s's Spegel P2P registry mirror — but that flag alone does *not* mirror anything; a registry only mirrors once it is listed under `mirrors:` in `/etc/rancher/k3s/registries.yaml`, generated by `k3s_registries()` as a bare `"*"` wildcard (mirror every registry via the embedded mirror, no endpoint overrides). `embedded-registry` is distributed cluster-wide from the server, but the `registries.yaml` mirror config is NOT — so it must be present on servers AND agents, which is why it is baked into the image (see `verb_image.py`) rather than pushed per join. Called by `verb_image.py` (writes inspection copies under `lib/manifests/` — gitignored/generated, never edit directly) and by `kopsrox_k3s.k3s_join()` (writes the real, node-specific `config.yaml` at join time via the guest agent).
- `lib/verb_image.py` — `image create` builds the microvm template and bakes in everything that is identical across every node in the cluster: writes a patched copy of `pve-microvm-template` to `lib/scripts/microvm-template.sh` (upstream's first-boot installer would block the guest agent behind a network that doesn't exist yet, and its chroot resolver is not the one kopsrox wants — each patch is asserted so upstream changes fail loudly, which is exactly how the 0.3.22 upgrade announced itself), runs it (`--disk-size 4G` for the bake headroom — the clone grows the root fs to `vm_disk` anyway — plus `--memory`/`--cores` from `vm_ram`/`vm_cpu`, `--bridge` from the (sdn-normalised) `network_bridge` so the template is built and booted on the same bridge its clones will use — without it the build silently defaults to `vmbr0` and the in-template k3s download fails on any host whose k3s network isn't `vmbr0` — and the chroot's `/etc/resolv.conf` written with the configured `network_dns`. Two patches went away at 0.3.22: upstream now repairs an empty/dangling OCI `/etc/resolv.conf` itself (with the *host's* resolver or `1.1.1.1`, hence the surviving dns patch) and runs the chroot package install fail-closed — `set -e` plus `die` on a failed transaction instead of `2>/dev/null` — which is what kopsrox's two apt patches used to buy, so a bad `extra_packages` now aborts the build loudly rather than yielding a bare template), verifies the rootfs actually has systemd + qemu-ga by ro-mounting the template disk, `sudo qm set --args` to boot the kopsrox kernel (`args` is root-only, so shell not API), then boots the template once via the guest agent to: run the k3s installer twice with `INSTALL_K3S_SKIP_START`/`INSTALL_K3S_SKIP_ENABLE` — once as `server` (produces `k3s.service`, shared by master/slave), once as `agent` (produces the separate `k3s-agent.service` for workers) — create the `localuser` account (password, SSH key, sudoers), write `/etc/resolv.conf` (`network_dns`), `mkdir` the baked-in `/etc/rancher/k3s` (so `k3s_join()` only pushes `config.yaml`, no per-join mkdir) and `/var/lib/rancher/k3s/server/manifests`, write the kube-vip/traefik manifest (plus, when `nfs_server` is set, the optional nfs-subdir-external-provisioner + `nfs` StorageClass — see `kopsrox_artifacts.kopsrox_nfs_manifest()`), and write the `registries.yaml` (`kopsrox_artifacts.k3s_registries()`, the embedded-mirror wildcard — baked here so it is present on every clone, server and agent alike) — before a graceful agent-driven shutdown and tagging. `extra_packages` are NOT apt-installed live after boot any more; they are folded into the template's single chroot `apt-get install` (`patch_microvm_template()` appends them to the `PKGS=` line), always plus `vim-tiny` (a usable editor for debugging over console/ssh) and `unzip` (so `cluster restore` can decompress a legacy compressed `.zip` snapshot), and plus `nfs-common` whenever `nfs_server` is set (the `nfs` StorageClass mounts via kubelet on the host, which needs the `/sbin/mount.nfs` helper; the built-in kernel NFS client alone is not enough, and `extra_packages` may be blank) — one apt transaction at build time, no post-boot network dependency for packages. The upstream package set is trimmed of `isc-dhcp-client` (unused on the apt path — systemd-networkd's built-in DHCP client serves the fresh clone's initial lease). Only genuinely per-node state (static IP, hostname, machine-id, root fs resize) is left to `node_prepare()`/`kopsrox_k3s.k3s_join()` at clone/join time. Bumping `k3s_version`, `localuser`/`localpass`/`localsshkey`, `network_dns`, `extra_packages`, or `nfs_server`/`nfs_path` in the ini now requires `image create` before it takes effect (previously they took effect on the next node join).
- `lib/verb_image.py` ( `image destroy` ) — idempotent: `NO_IMAGE_CMDS` in `kopsrox_config` exempts it from init's "image not found" abort alongside `image create` and `config check`, and it returns early when `cluster_id` is absent from `disc_vms`. A destroy whose target is already gone has done its job, so it exits 0 rather than 1 — and the early return also skips `kopsrox_img()`, whose `pvesm` fallback would be a ~1.4s spawn to look up a disk that is not there.
- `lib/verb_config.py` — `config check`, the one place the full checks run. It also runs the one check that goes the *other* direction from `validate()`: `kopsrox_schema.unknown_options()` reports entries present in `kopsrox.ini` that are not in SCHEMA ( plus any section other than `[kopsrox]` ). validate() only ever asks "is every option kopsrox knows about present and sane" — a misspelt option name is invisible to it, `ConfigParser` just ignores the extra key, and if the typo shadows a `commented` option the real one quietly falls back to its default. It re-reads the ini rather than threading the parser out of init(), which costs a file read and keeps `unknown_options()` pure and testable. It warns rather than aborts: an unknown key is inert at runtime, and aborting would break anyone keeping their own notes in the file. init() keeps only what every command needs (ini validation, storage/image existence, the drift hint); this verb prints the drift detail and makes the two network calls (`microvm_release_notice()`, `kernel_notice()`). It is exempt from init's "image not found" abort so it works on a fresh install, before the first `image create`.
- `lib/verb_node.py` — `node ssh` passes `UserKnownHostsFile=/dev/null` as well as `StrictHostKeyChecking=no`, because the latter alone auto-accepts a *new* key but hard-refuses a *changed* one — and every rebuild at a fixed IP changes it, so a recorded key breaks `node ssh` until the entry is cleared by hand. `ConnectTimeout` bounds the banner exchange as well as the TCP connect, which is the one case that otherwise hangs forever ( a node that accepts the connection then goes quiet; a powered-off node on the local subnet already fails in ~3s on ARP ). `node ssh`/`node terminal` use `subprocess.call` and exit on its return code - they hand a tty to an interactive program, so `pve_run()` ( which captures output ) is the wrong tool.
- `lib/kopsrox_kmsg.py` — the only module that emits ANSI; all user output goes through it. `kmsg(kname, msg, sev)` prints a glyph + severity-colored line (`kname` is `scope_action`, split on the first `_`; `sev` is `info`/`sys`/`err`); `kabort(kname, msg)` is `err` + `exit(1)`; `kstep(kname, msg)` is a context manager showing a live spinner with elapsed time (`quiet=True` for polling internals like `qa_exec` — nothing printed on success); `kplan(add, title)`/`kplan_tick()` drive the overall `4/9` progress bar in compound verbs (`cluster create/update/restore/destroy`, `image create`). Output degrades to plain sequential lines when stdout is not a tty; `NO_COLOR` disables color. `dev/test_kmsg.py` tests the module standalone (scripted asserts when piped, visual demo on a tty).

VM ID / naming convention (defined by `suffixes`/`vmnames` in `kopsrox_config.py`): `cluster_id` = template `-i0`, `+1..+3` = masters `-m1..-m3` (m1's ID is `masterid`), `+4` = utility `-u1`, `+5..+9` = workers `-w1..-w5`. Each VM's IP is derived arithmetically: `network_ip`'s last octet + (vmid − cluster_id). `network_ip` itself is the kube-vip VIP. Only 1 or 3 masters are supported.

Microvm specifics and traps (each of these was learned the hard way):

- `machine: microvm` with direct kernel boot — no BIOS/UEFI, no cloud-init drive, no `boot=order`. Static IP/MTU is applied in-guest by `node_prepare()` via the agent (`ipconfig0`/`net0 mtu=` are no-ops for microvms); DNS and the local user are baked into the image instead (see `verb_image.py`).
- The guest kernel is custom-built (`dev/build-kopsrox-kernel.sh` + `lib/scripts/kopsrox-kernel.config`) because guests have no `/lib/modules` — every feature k3s needs must be `=y`. When adding kernel options, audit the final `.config`: `olddefconfig` silently drops options with unmet dependencies (most `xt_*` need `NETFILTER_ADVANCED=y`).
- The kopsrox kernel's built-in DUMMY/SIT create `dummy0`/`sit0` in guests, so network matching must use `Driver=virtio_net`, never `Type=ether` (which once assigned the node IP to dummy0 and blackholed the default route).
- Guests boot in ~1s. The 90s-boot failure mode is udev missing from the image (device units never appear, `serial-getty` waits on `dev-ttyS0.device` forever) — the template installs udev/sudo/systemd-timesyncd on top of upstream's package set, plus `net.ifnames=0` on the kernel cmdline so udev doesn't rename `eth0` (kube-vip's manifest hardcodes it).
- The enforced floor is pve-microvm **0.3.24**, and each of the three steps buys something kopsrox actually depends on: 0.3.22 is the template layout `patch_microvm_template()` anchors on; 0.3.23 fixed linked-clone disk-format detection (`clone()` runs `qm clone` with no `--full` against a base volume, so *every* kopsrox node is a linked clone — before 0.3.23 pve-microvm called a nonexistent `PVE::Storage::volume_format()` and fell back to raw, booting a file-backed qcow2 clone through the wrong QEMU block driver; LVM-thin/ZFS are raw anyway so it cannot bite there, but `proxmox_storage` is free-form and dir/NFS would corrupt); 0.3.24 keeps exactly one `qemu-guest-agent.service` and drops the competing `microvm-agent` unit, which matters because every in-node operation kopsrox performs goes through that agent. The floor stays at 0.3.24 — nothing in 0.3.25 is a capability kopsrox needs — but 0.3.25 does tighten `--refresh` to `die` unless the target vmid is an existing *stopped template*, and kopsrox defers the `qm template` conversion to the end of `image_create()`, so a build interrupted before that point leaves i0 a plain ( usually running ) VM that `--refresh` would then refuse forever. `image_create()` therefore destroys an existing i0 itself before invoking the template script, and `prox_destroy()` stops any VM ( i0 included ) before destroying it. 0.3.26-0.3.29 add nothing kopsrox needs either ( 0.3.29 fixes a machine-version parse on *full* clones from a *running* microvm — kopsrox only ever linked-clones a stopped template ), so the floor is still 0.3.24, but two of them change its environment: 0.3.27 routes the template script's scratch through `pve-microvm-env.sh`, whose resolver lands on `/tmp` — tmpfs on a stock pve node, so the extracted rootfs and the raw/qcow2 disk would be built in RAM next to the running cluster; `image_create()` therefore invokes the script under `sudo env PVE_MICROVM_TMP_ROOT=/var/cache/pve-microvm`, the pre-0.3.27 location. ( the patched copy lives in `lib/scripts/`, where upstream's `dirname $BASH_SOURCE/pve-microvm-env.sh` probe misses and falls through to the installed `/usr/share/pve-microvm` copy — that fallback is what keeps the patched copy runnable from the repo. ) 0.3.27's env refactor reaches `kernel/build-kernel.sh` too, and there it is not optional: the script sources the helper from a sibling `tools/` directory and now *rejects* an `--output` that is not below its own `$PVE_MICROVM_BUILD_DIR`, so `dev/build-kopsrox-kernel.sh` mirrors the upstream checkout layout ( `kernel/` + `tools/lib/` ) under its work dir, pins `PVE_MICROVM_TMP_ROOT` there and builds into it. 0.3.27 and 0.3.28 also reconfigure the *guest kernel* — Landlock, then built-in EROFS — see the kernel bullet below. 0.4.0/0.4.1 again add nothing kopsrox needs: 0.4.0 moves the guest kernel to 6.12.113 ( the version now lives in `kernel/version`, and `build-kernel.sh` runs extra `check-*.sh` scripts — `dev/build-kopsrox-kernel.sh` must fetch every file it references ) and 0.4.1 adds `udev` to the template's `PKGS=` line ( the anchor `patch_microvm_template()` matches ) and makes AppArmor the kernel's default major LSM. AppArmor on with no `apparmor_parser` in the image makes containerd fail every pod, so `image create` boots guests with `apparmor=0`.
- `qm stop` is a hard power-cut (no ACPI): guest page-cache writes are lost, so never stop a node to "check" something that was just written inside it. Debug live — the serial console accepts input only with `\r` line endings (via socat on `/var/run/qemu-server/<vmid>.serial0`).
- `qm shutdown`/`qm reboot` need pve-microvm ≥ 0.3.19 (our upstream fix: qmeventd socket + dbus; #13/#14). the only guest reboot kopsrox still issues is the `node reboot` command, via `node_reboot_wait()` (in-guest `systemctl reboot`, detected by boot-id change — microvms reboot too fast for agent-down polling). `node_prepare()` no longer reboots (identity/network applied live). A VM stuck in `paused (shutdown)` recovers with `qm stop` + `qm start`; likewise an agent left wedged after a reboot (guest `running` but `qemu-ga not running`).
- `node_reboot_wait()`'s own timing is inherently variable (measured 7.9s/35.3s/27.9s on three consecutive reboots of the same already-stable node, nothing else running) — this is virtio-serial/qemu-guest-agent reconnection variance after a guest kernel reboot, not the guest itself being slow (`systemd-analyze` on the same node confirms the guest boots in ~1.1s every time). This variance/wedge risk is exactly why `node_prepare()` was changed to apply live rather than reboot; it now only bites the explicit `node reboot` command.
- pvedaemon holds pve-microvm's perl code in memory: on pve-microvm < 0.3.20, `systemctl restart pvedaemon` after install/upgrade or the API/web-UI silently run the old code (0.3.20+ postinst restarts it itself; 0.3.22 also `try-restart`s it from the package-configure and qemu-server trigger paths, so a long-lived worker no longer keeps a stale `MicroVM.pm`; 0.3.26 softened that to `deb-systemd-invoke reload-or-try-restart` because the hard restart was killing the web UI's own terminal children mid-`apt`). Moot at the enforced 0.3.24 floor, kept as background. kopsrox itself is now immune — it drives VMs through `qm`, a fresh process that loads the current code every invocation — but restart pvedaemon anyway so the web UI/API match.
- Every node's image has BOTH `k3s.service` and `k3s-agent.service` baked in (so any clone can become master/slave or worker) — this means k3s's own `k3s-uninstall.sh`/`k3s-agent-uninstall.sh` must never be used to remove k3s from a node: its "another k3s service installed" guard always trips (both units always exist) so it skips cleaning up the shared binary/data, and it unconditionally deletes its own unit file first regardless, which nothing can regenerate short of an `image create`. `node_k3s_uninstall()` uses the generic, role-agnostic `k3s-killall.sh` instead and wipes `/var/lib/rancher`/`/etc/rancher/k3s` by hand then recreates the ( baked-in ) `/etc/rancher/k3s` dir so the next `k3s_join()` has somewhere to push `config.yaml`, leaving the baked-in units untouched for that rejoin to reuse.

Error-handling convention: errors go through `kabort(kname, msg)` — an `err` line then `exit(1)`; success paths exit 0. Broad `except Exception:` around attribute/index access is still common (no bare `except:` remains in `lib/`/`kopsrox.py`, so `SystemExit`/`KeyboardInterrupt` always propagate); SystemExit-as-control-flow (an `exit()` inside `try` caught by a broad `except`) has been removed — don't reintroduce it.

## Cluster artifacts in repo root

`<cluster_name>.kubeconfig` and `<cluster_name>.k3stoken` are exported per cluster and are required for restore operations. Etcd snapshots go to the S3 endpoint configured in the ini; `cluster restore [snapshot]` rebuilds the whole cluster from a named snapshot ( names come from `etcd list` ), or the latest when none is given, purging stale node objects/password secrets before rebuilding workers — it queries the restored datastore ( `kubectl get nodes` ) for what's actually there and drops all but the restored master, rather than trying every name in the kopsrox convention. There is no separate `etcd restore` — restore is always `cluster restore`, which rebuilds every node, not just the master.


## General

Never commit as Claude always use the details im users .gitconfig

**Keep comments minimal.** The codebase was deliberately cut from 657 comment lines to 125 — do not grow it back. Default to no comment: the code, the function name and CLAUDE.md should carry the meaning. Comment density is a budget, not a free resource, so adding one anywhere is a reason to check whether an older one nearby has become redundant.

Write a comment only when it says something a reader cannot get from the code, and keep it to one or two lines:

- **a trap** — where the obvious "fix" would break something. The saved token being mandatory for `--cluster-reset`, `\bReady\b` needing the word boundary because plain `Ready` matches `NotReady`, never using `k3s-uninstall.sh`, the `exit 0` on the discovery spawn, the explicit `\r\n` in `kmsg`.
- **a non-obvious cost** — the ~1.4s pve-perl spawn, the fixed ~0.5-1s guest-agent round trip. These explain why code is shaped oddly for speed.
- **an external contract** — a bzImage header offset, a pve conf format, a k3s flag's semantics.

Do NOT write:

- restatements of the next line (`# destroy vm` above `prox_destroy()`, `# define kname`, `# return sorted dict`)
- history or changelog — what the code used to do, how many round trips it took before batching, which upstream release changed it, what bug a line once fixed. That belongs in the commit message and git log.
- rationale already recorded in this file. Link the concept by name instead of restating the reasoning inline.

When editing, prefer deleting a stale comment to updating it. If a comment block has grown past ~4 lines, it is documentation — move it here and leave a pointer.
